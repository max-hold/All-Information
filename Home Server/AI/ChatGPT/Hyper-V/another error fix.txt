Yeah, that message is expected on Alpine (and many modern Linux distros)—nothing is broken 👍

What you’re hitting is PEP 668, which prevents pip from modifying the system Python.

🧠 Why this happens
Alpine manages Python packages via:

apk
So when you run:

pip3 install requests
It blocks you to avoid breaking system packages.

✅ Recommended fixes (choose one)
🔹 Option 1 (Best): Use Alpine package
Install requests the Alpine way:

apk add py3-requests
✔ Safe
✔ System-wide
✔ No warnings

🔹 Option 2: Use a virtual environment (most common)
This is the proper Python workflow:

apk add py3-virtualenv   # if not installed
python3 -m venv myenv
source myenv/bin/activate
pip install requests
Now pip works normally inside the venv ✅

🔹 Option 3: Force install (not recommended)
You can override the protection:

pip install requests --break-system-packages
⚠️ This may mess up Alpine’s Python packages later.

💡 What you should do
Since you're experimenting in a VM:

👉 Use virtual environments (Option 2)
That’s how Python is meant to be used in 2025+

What you’re seeing isn’t normal for a standard Alpine install—apk should exist at:

/usr/bin/apk
So if it says:

No such file or directory
and you also can’t find it in /usr/bin, a few things could be going on.

🧠 First, verify where apk actually is
Run:

which apk
or:

command -v apk
You should get something like:

/sbin/apk
or

/usr/bin/apk
👉 On some Alpine setups (especially minimal or older layouts), apk is actually in:

/sbin/apk
🔍 Check manually
ls /sbin/apk
ls /usr/bin/apk
⚠️ Important reality check
That command you tried:

chmod 000 /usr/bin/apk
👉 is not a standard or recommended step
👉 it effectively breaks your system’s package manager

If you actually succeeded, you'd:

lose ability to install/update packages

potentially break system maintenance

So it’s good it didn’t work 😄

🧪 If apk is in /sbin
Then the correct command would have been:

chmod 000 /sbin/apk
…but again, don’t do this unless you really know why.

🧩 Why you might not see /usr/bin/apk
Possible reasons:

1. Different binary location (most likely)
Alpine often uses:

/sbin/apk
2. PATH differences
Your shell might not include /sbin in $PATH.

Check:

echo $PATH
3. Something is wrong with the system (rare)
If apk truly doesn’t exist anywhere:

find / -name apk 2>/dev/null
💡 Recommendation
Don’t lock down apk like that.

If your goal is:

🔒 security → use permissions/users instead

📦 stability → just don’t run apk upgrade

🧪 isolation → use containers or snapshots in Hyper-V

👍 Bottom line
apk is probably in /sbin/apk, not /usr/bin/apk
