Critical — VM will not boot
CRITICAL
Missing initrd — kernel won't find the root filesystem
Part 5 › vm-config.json + launch scripts
▸
Cloud Hypervisor uses direct kernel boot (not BIOS/UEFI). Direct kernel boot requires both a kernel image and an initrd (initial ramdisk). The initrd unpacks early userspace, loads kernel modules, and mounts the real root filesystem. Without it, the kernel panics immediately at boot with VFS: Unable to mount root fs.
Fix — add initrd to every launch command and vm-config.json
--kernel /boot/vmlinuz \
--kernel /boot/vmlinuz-$(uname -r) \
--initramfs /boot/initrd.img-$(uname -r) \
Important: see error #2 — the host kernel itself is also wrong here. Both must be extracted from the guest image.
CRITICAL
Host kernel used to boot guest — incompatible modules and ABI
Part 5 › vm-config.json, all launch scripts
▸
The guide points the guest kernel at /boot/vmlinuz — the host's own kernel. A cloud image guest needs its own kernel built with virtio drivers and the matching guest ABI. The host kernel may lack these modules entirely, and even if it boots, kernel/module version mismatches will cause driver failures. The correct approach is to extract the kernel and initrd from the downloaded cloud image itself.
Fix — extract kernel and initrd from the cloud image
sudo modprobe nbd
sudo qemu-nbd --connect=/dev/nbd0 ubuntu-browser.img
sudo mount /dev/nbd0p1 /mnt/guest

KERNEL=$(ls /mnt/guest/boot/vmlinuz-* | tail -1)
INITRD=$(ls /mnt/guest/boot/initrd.img-* | tail -1)
cp $KERNEL ./guest-vmlinuz
cp $INITRD ./guest-initrd.img

sudo umount /mnt/guest
sudo qemu-nbd --disconnect /dev/nbd0

# Then launch with:
--kernel ./guest-vmlinuz \
--initramfs ./guest-initrd.img \
Alternatively, download a cloud-hypervisor-compatible kernel from the upstream releases page.
CRITICAL
Broken password hash in cloud-init — login will fail silently
Part 3 › user-data (passwd field)
▸
The password hash $6$rounds=4096$saltsaltsal$L7gFZEq... is a truncated, fabricated hash. SHA-512 hashes are 86 characters of base64 after the salt — this one is cut short. Cloud-init will either reject it or create the account with an invalid password, locking you out of the VM entirely on first boot.
Fix — generate a real hash with openssl or python3
# Generate a proper hash first:
python3 -c "import crypt; print(crypt.crypt('browser123', crypt.mksalt(crypt.METHOD_SHA512)))"
# or
openssl passwd -6 browser123

# In user-data, use the full output:
passwd: $6$RaNd0mSaLt$FULL_86_CHAR_HASH_HERE

# Simpler alternative — use plain_text_passwd (dev only):
plain_text_passwd: browser123
lock_passwd: false
CRITICAL
TAP device not accessible to cloud-hypervisor process
Part 4 › setup-network.sh + all launch scripts
▸
The TAP device is created with sudo ip tuntap add but the launch scripts run cloud-hypervisor without sudo. The process won't have permission to open the TAP file descriptor. Either run cloud-hypervisor as root (not recommended) or use the user flag on tuntap creation and add the user to the kvm group.
Fix — create TAP device owned by the current user
sudo ip tuntap add tap-ch0 mode tap
sudo ip tuntap add tap-ch0 mode tap user $USER group kvm
sudo usermod -aG kvm $USER  # if not already done

# Also ensure /dev/kvm is accessible:
sudo chmod 666 /dev/kvm
# or add yourself to the kvm group and re-login

Configuration errors
CONFIG
vm-config.json net section mixes TAP name with static IP — conflicting fields
Part 5 › vm-config.json
▸
When you specify "tap": "tap-ch0" in Cloud Hypervisor's net config, you are binding to an existing TAP device. The ip and mask fields in the same block are for Cloud Hypervisor to configure an internally-managed TAP — they conflict and will cause a config validation error or be silently ignored, depending on the CH version.
Fix — use either an existing TAP or let CH manage the device, not both
"net": [
  {
    "tap": "tap-ch0",
    "mac": "12:34:56:78:90:ab"
    "ip": "192.168.100.2",
    "mask": "255.255.255.0"
  }
]
Guest IP is assigned by DHCP from your host-side DHCP server (or configured statically inside the guest). The net config section is not the place to set guest IP when using an external TAP.
CONFIG
Cloud-init network-config uses enp0s3 — virtio-net interface is named differently
Part 3 › Step 3.2 network-config
▸
Ubuntu cloud images with predictable network interface naming will name the first virtio-net device ens3 or enp1s0 inside a Cloud Hypervisor VM — not enp0s3. enp0s3 is the VirtualBox naming convention. With the wrong interface name, cloud-init network config does nothing and DHCP may not run.
Fix — use a wildcard match or the correct virtio interface name
version: 2
ethernets:
  enp0s3:
  ens3:        # typical Cloud Hypervisor virtio-net name
    # or use: enp1s0
    dhcp4: true

# Safest option — match all ethernet devices:
  id0:
    match:
      name: "en*"
    dhcp4: true
CONFIG
X server started without a display config — xorg.conf doesn't exist in the guest
Part 5 › launch-vnc.sh (SSH heredoc)
▸
The script runs sudo X :0 -config /etc/X11/xorg.conf inside the VM. A cloud image has no physical display, so /etc/X11/xorg.conf doesn't exist. X will exit immediately. For a headless/VNC setup, you need a dummy display driver config.
Fix — create a dummy xorg.conf before starting X
sudo apt install -y xserver-xorg-video-dummy
sudo tee /etc/X11/xorg.conf > /dev/null << 'XCONF'
Section "Device"
  Identifier "DummyDevice"
  Driver "dummy"
  VideoRam 256000
EndSection
Section "Screen"
  Identifier "DummyScreen"
  Device "DummyDevice"
  DefaultDepth 24
  SubSection "Display"
    Depth 24
    Modes "1920x1080"
  EndSubSection
EndSection
XCONF
sudo X :0 -config /etc/X11/xorg.conf &

Part 3 › Step 3.1
▸
The guide resizes the downloaded image first, then copies it. This permanently modifies the original download, so you can't re-use it to create a fresh VM or a different size without re-downloading.
Fix — copy first, resize the copy

Logic / flow errors
LOGIC
VNC port inconsistency throughout the guide — 5900 vs 5901
Part 5 Step 5.2 vs Part 7 Step 7.1
▸
launch-vnc.sh connects to port 5900 (x11vnc default, display :0). Step 7.1 tells the user to connect to port 5901 (tightvncserver display :1). These are two different VNC approaches — the guide mixes them up. A junior engineer following both sections in order will get a connection refused error.
Fix — pick one VNC method and use it consistently
# If using tightvncserver (recommended — more stable):
vncserver -geometry 1920x1080 -depth 24   # starts on :1 → port 5901
vncviewer 192.168.100.2:5901

# If using x11vnc (display :0 → port 5900):
x11vnc -display :0 -forever -shared -nopw
vncviewer 192.168.100.2:5900
LOGIC
Two conflicting VNC methods defined — x11vnc in launch script, tightvncserver in Step 6.2
Part 5 Step 5.2 vs Part 6 Step 6.2
▸
launch-vnc.sh SSHes into the VM and installs/starts x11vnc. Step 6.2 installs tightvncserver and sets up startxfce4. These are mutually exclusive workflows with different ports, startup methods, and desktop environments. Running both will cause port conflicts and configuration chaos.
Fix — use tightvncserver + XFCE consistently (more reliable for desktops)
# Remove the x11vnc section from launch-vnc.sh entirely.
# In cloud-init user-data, add to runcmd:
  - apt install -y tightvncserver xfce4 xfce4-goodies
  - su -c 'vncserver -geometry 1920x1080 -depth 24' browser
# And pre-create ~/.vnc/xstartup via write_files in cloud-init
LOGIC
SSH heredoc won't reliably start background processes in the VM
Part 5 › launch-vnc.sh
▸
The script uses sshpass ssh ... << 'REMOTE' to start X and VNC inside the VM as background processes. When the SSH session closes, those background jobs are killed (SIGHUP). The X server and VNC will die the moment the heredoc finishes, before vncviewer can connect.
Fix — use nohup or a systemd unit, or separate SSH commands with -f
sshpass -p 'browser123' ssh -o StrictHostKeyChecking=no \
  -f browser@$VM_IP \
  "nohup Xvfb :1 -screen 0 1920x1080x24 &>/dev/null & \
   sleep 2 && \
   nohup x11vnc -display :1 -forever -shared -nopw &>/dev/null &"
# -f forks SSH into background after auth but before command exits
LOGIC
benchmark.sh uses ping to measure boot — measures network up, not boot complete
Part 10 › benchmark.sh
▸
The benchmark waits for a successful ping to declare boot complete and records that as BOOT_TIME. Ping responds as soon as the network interface initialises — which happens long before cloud-init, the desktop, xrdp, or VNC are ready. The measured time is meaningless for the stated goal of running Firefox.
Fix — wait for SSH or the VNC port to confirm a fully-booted guest
while ! ping -c 1 192.168.100.2 &>/dev/null; do sleep 0.1; done
while ! nc -z 192.168.100.2 22 2>/dev/null; do sleep 0.5; done
echo "SSH port open — cloud-init may still be running"
# For full readiness, wait for port 5901 (VNC) or 3389 (RDP)
PERFORMANCE
Performance expectations are off by 10-40x — misleading for capacity planning
Part 10 › Expected Performance section
▸
The guide claims "VM boot time: 100–150ms" and "total to browser: 2–3 seconds". Cloud Hypervisor's hypervisor initialisation is ~100ms, but a full Ubuntu cloud image with desktop packages, cloud-init, xrdp/VNC startup, and Firefox launch realistically takes 45–120 seconds on first boot, and 20–60 seconds on subsequent boots.
Corrected realistic estimates
Cloud Hypervisor hypervisor init:   ~100–200ms
Ubuntu guest kernel + initrd boot:  ~3–8 seconds
cloud-init (first boot, apt installs): 5–15 minutes
cloud-init (subsequent boots):       30–90 seconds
Desktop + VNC/xrdp ready:            +10–30 seconds
─────────────────────────────────────────────────
First boot total:                   ~10–20 minutes
Subsequent boot to browser ready:   ~60–120 seconds
Security issues
SECURITY
Hardcoded plaintext credentials in scripts and source files
launch-vnc.sh, launch-spice.sh, file-monitor.py, user-data
▸
The password browser123 appears in shell scripts, Python source, and cloud-init configs in plaintext. For an "isolated browser" security tool, this defeats the purpose — any process that can read these files has the VM credentials. Scripts will also end up in shell history.
Fix — use SSH keys and environment variables
# Generate SSH key for VM access (no password)
ssh-keygen -t ed25519 -f ~/.ssh/ch_browser -N ""

# In cloud-init user-data, add the public key:
ssh_authorized_keys:
  - $(cat ~/.ssh/ch_browser.pub)

# In scripts, use key-based auth:
ssh -i ~/.ssh/ch_browser browser@$VM_IP

# Store sensitive values in environment, not source:
export VM_PASSWORD="$(pass show browser-vm)"  # or use a secrets manager
SECURITY
StrictHostKeyChecking=no disables MITM protection on every SSH connection
Part 5 › launch-vnc.sh
▸
Using -o StrictHostKeyChecking=no tells SSH to accept any host key without verification. Even on a local network, this is poor practice — it prevents detection of IP reuse or ARP spoofing. The guide uses this as a lazy workaround for the re-provisioned VM getting a new host key.
Fix — use a known_hosts file scoped to the VM's MAC address
ssh -o StrictHostKeyChecking=no browser@$VM_IP
# After first boot, trust the key explicitly once:
ssh-keyscan -H $VM_IP >> ~/.ssh/known_hosts_chvm

# Then in all SSH calls:
ssh -o UserKnownHostsFile=~/.ssh/known_hosts_chvm \
    -i ~/.ssh/ch_browser browser@$VM_IP
SECURITY
paramiko.AutoAddPolicy() in file-monitor.py disables host verification
Part 8 › file-monitor.py
▸
ssh.set_missing_host_key_policy(paramiko.AutoAddPolicy()) is the paramiko equivalent of StrictHostKeyChecking=no — it blindly accepts any host key. For a security-oriented tool, this should use RejectPolicy with a pre-loaded known_hosts file.
Fix — load known host keys explicitly
ssh.set_missing_host_key_policy(paramiko.AutoAddPolicy())
ssh.set_missing_host_key_policy(paramiko.RejectPolicy())
ssh.load_host_keys(os.path.expanduser('~/.ssh/known_hosts_chvm'))
